# NIP-46 interop notes: window.nostr.js, Amber, and Croissant

Status: reproduced and deployment-tested, 2026-07-29. No private keys, bunker URIs, client
secrets, or complete ephemeral connection events are included here.

## Versions tested

- `window.nostr.js` 0.8.1 at `54f8d47116d19b5e64c0aef6b24df7d53f947cd7`
- `@nostr/tools` 2.23.8 (the relevant NIP-46 implementation is unchanged in
  upstream 2.24.0)
- Amber 6.3.0
- Mosaico v0.1.2
- Croissant `c55533d0e7fd`

## 1. Successful `nostrconnect://` handshake does not finish queued login

### Observed

Amber receives the request on the configured relays and returns the correct
NIP-46 secret. `BunkerSigner.fromURI()` resolves, but the web application can
remain logged out or a queued `window.nostr.signEvent()` can reject with:

```text
No Promise in Promise.any was resolved
```

The browser has already received the kind 24133 connection response when this
happens.

### Upstream-ready patches

The fix has been split into two reviewable branches:

- `fix/nip46-qr-pending-calls` at `74445af`: marks the widget connected when
  `BunkerSigner.fromURI()` resolves, resolves the signer, flushes queued NIP-07
  calls, awaits identity discovery, and then closes the widget.
- `fix/amber-nip46-relay-compat` at `be30d8a`: a stacked compatibility patch
  that sets `skipSwitchRelays: true` for the initial Amber connection.

The first patch made Croissant's top login button complete after Amber approved
the connection. Both branches pass `just build`.

### Upstream direction

The UI state/queue completion belongs in `window.nostr.js`. The relay-switching
failure is probably better fixed in `nostr-tools`: automatic `switch_relays`
should not replace a working connection with an empty or unusable relay set.
The current `skipSwitchRelays` option is a compatibility workaround and should
not become the general NIP-46 policy without discussion.

## 2. Amber can transiently report `Invalid nostr connect URI` for a valid QR

### Observed

Amber 6.3.0 displayed `Invalid nostr connect URI` immediately after scanning a
fresh QR generated by `window.nostr.js`.

A later scan of a fresh QR succeeded and Mosaico login completed. Treat this as
an intermittent scanner/interoperability report, not a confirmed URI-generation
defect.

The tested URI had this redacted shape:

```text
nostrconnect://<64-lowercase-hex-client-pubkey>
  ?relay=<four percent-encoded wss URLs>
  &secret=<16-hex-secret>
  &name=<host>
  &url=<page URL>
  &image=<favicon URL>
```

It was 340 bytes on localhost. JavaScript `URL` parsing confirmed the scheme,
64-hex pubkey, four relay values, and secret. An independent `zbarimg` decode of
the rendered QR had the same SHA-256 as the exact URI displayed by the widget.

Amber's `NewApplicationScreen` shows this warning only when the scanner returns
blank content or content not beginning exactly with `nostrconnect://`; the later
NIP-46 parser does not produce this warning. This therefore looks like a scanner
false-negative/corrupted scan, not a malformed Mosaico or Croissant URI.

### Next evidence to collect

On the next occurrence, record whether:

1. Amber immediately shows the warning before an approval screen;
2. a new application appears in Amber;
3. pasting the exact URI through Amber's **Paste from clipboard** path succeeds;
4. enlarging the QR or removing optional `url` and `image` metadata changes the
   result.

Do not publish the complete URI: its `secret` is a one-time authentication
value.

### Upstream direction

- Amber issue: include scanner result diagnostics (blank, prefix, decoded
  length) without logging the full URI or secret; consider trimming surrounding
  whitespace before the prefix check.
- `window.nostr.js` enhancement: offer a larger QR and a compact URI mode that
  omits optional metadata. This is not yet proven necessary and should not be
  mixed into the handshake-state fix.

## 3. Croissant opens a NIP-29 address in Grimoire's generic event route

### Observed

Croissant linked groups as `https://grimoire.rocks/<naddr>`. Grimoire accepts
that route, but it displays the kind 39000 address as a generic event instead of
opening the group chat.

Grimoire's NIP-29 command route is:

```text
https://grimoire.rocks/run?cmd=chat%20<naddr>
```

### Upstream-ready patch

- Croissant branch `fix/grimoire-chat-deep-link` at `a4692d9` changes both the
  template source and generated Go output to use the chat command route.
- `go test ./...` passes.
- The corrected link is deployed on the Mosaico v0.1.2 host and returns the
  existing `infra` group chat address.

This belongs in Croissant, not Mosaico.

## 4. Nostrord login is not yet isolated

Current Nostrord source already excludes `wss://relay.nsec.app` from its QR
defaults and advertises `wss://relay.damus.io` plus `wss://nos.lol`. A fresh QR
from the current web deployment had the expected `nostrconnect://` structure.

Pasting an Amber-created bunker URI can still fail if that URI advertises
`wss://relay.nsec.app`, which returned HTTP 502 during the earlier test. That is
different from Nostrord's own fresh-QR flow.

Before filing a Nostrord issue, collect one fresh-QR attempt with:

1. whether a Nostrord application appears in Amber;
2. Amber's redacted request/response timestamps and relay names;
3. whether Nostrord remains on the QR screen after Amber responds;
4. browser console errors at the matching time.

Do not include the QR URI, connection secret, bunker URI, or full kind 24133
events in an issue.

## Suggested upstream issue: preserve a working relay set during `switch_relays`

Repository: `nbd-wtf/nostr-tools`

Title: `BunkerSigner.fromURI can strand a working NIP-46 connection after switch_relays`

Body:

> With `@nostr/tools` 2.23.8, `BunkerSigner.fromURI()` successfully completes an
> Amber 6.3.0 `nostrconnect://` handshake over the relays encoded by the client.
> The signer then requests `switch_relays`; replacing the established relay set
> can leave subsequent queued calls with no usable response path. The caller
> eventually sees `No Promise in Promise.any was resolved` even though the
> connection response was received and decrypted.
>
> Passing `skipSwitchRelays: true` avoids the failure, but prevents the signer
> from controlling relays as NIP-46 intends. Could the implementation validate
> the proposed relay set and retain the established relays as fallback until at
> least one proposed relay is usable?
>
> Reproduction versions: Amber 6.3.0, `@nostr/tools` 2.23.8,
> `window.nostr.js` 0.8.1. No private URI or event is required; redacted relay
> and timing logs can be supplied.

## Update assessment

- Mosaico v0.1.2 is still the latest release.
- Mosaico `master` contains unreleased changes that make Croissant external
  infrastructure, so it is not a drop-in login fix for this deployment.
- The newer Croissant BUD-11 commit does not touch NIP-46 or QR generation. The
  Grimoire route fix is based on that current upstream commit.
- Upstream `window.nostr.js` has no newer commit than the fork base.

No additional Mosaico source patch is justified by the login evidence above.
